# Fast Temp Mail — standalone deploy package

A deploy-ready temporary-email service with accounts, wallets and plans, built to run **outside** Muse on any host with Bun and PostgreSQL.

**Primary target: a 100% free stack, no credit card**

| Piece        | Free service | Free-tier limits you should know |
|--------------|--------------|----------------------------------|
| Web hosting  | **Render** (free web service) | 750 hrs/month · 512 MB RAM · **sleeps after 15 min idle** (first request after sleep takes ~30–60 s) · ephemeral disk · no credit card |
| Database     | **Supabase** (free PostgreSQL) | 500 MB database · no credit card · persists independently of Render |
| Domain (now) | **Free** `https://<name>.onrender.com` | included with Render |
| Domain (later) | Your **Hostinger** domain | connect anytime via DNS (step 6 below) |

> ⚠️ **Do NOT use Render's own free Postgres** — it expires (30-day trial). Point `DATABASE_URL` at Supabase instead; your data then survives Render restarts, redeploys, and the idle sleep.

## How it works

- **Server:** Bun (`server/src/index.ts`) — serves the built React SPA, exposes `POST /actions` (every app operation, validated with zod), and `GET /health`.
- **Database:** PostgreSQL via `postgres-js` + Drizzle. Migrations in `drizzle/` run automatically at boot; applied files are tracked in `_schema_migrations`.
- **Client:** React 19 + TanStack Query, built with `bun ./client/build.mjs` into `client/dist`. Black/blue/gold theme with a dark/light toggle.
- **Temp mail:** `generateTempEmail` creates addresses like `swift-fox-4821@fasttempmail.site` (display domain from `MAIL_DOMAIN`). Signed-in users' addresses are saved in the database; anonymous visitors' addresses are tracked in `localStorage`. **The inbox is simulated in this build** — see "Honest limitations".
- **Auth:** email/password with PBKDF2-SHA256 hashing, 6-digit OTP verification, Google OAuth (PKCE), opaque session tokens stored as SHA-256 hashes **peppered with `SESSION_SECRET`**.
- **Wallet & plans:** per-user USD wallet, crypto deposits (min $3, stay `pending` until manually verified), Free / Gmail ($2.50/mo) / Pro ($3/mo) plans, upgrades activated manually by an admin.
- **Admin:** seeded from `ADMIN_EMAIL` / `ADMIN_PASSWORD` on first boot only. No dev login bypass exists anywhere.

## Deploy — Render + Supabase (recommended, $0)

### 1. Create the free Supabase database

1. Go to [supabase.com](https://supabase.com) and create a free account (no credit card).
2. **New project** → name it `fasttempmail` → set a strong database password → create. Wait ~2 minutes for provisioning.
3. Project **Settings → Database → Connection string → URI** → copy it and replace `[YOUR-PASSWORD]` with the password from step 2.
4. For Render, use the **pooler** host (port `6543`). The final string looks like:
   `postgresql://postgres:YOUR-PASSWORD@db.YOUR-REF.supabase.co:6543/postgres?pgbouncer=true&sslmode=require`
   (The server detects the pooler and disables prepared statements automatically.)

### 2. Push this folder to GitHub

Create a new repo and push the contents of this folder (including `render.yaml` and `Dockerfile`).

### 3. Deploy on Render from the blueprint

1. [render.com](https://render.com) → free account (no credit card) → **New → Blueprint** → connect the repo.
2. Render reads `render.yaml` and proposes one **free** web service (Docker runtime). Click **Apply**.
3. Fill the prompted env vars:
   - `DATABASE_URL` — the Supabase string from step 1 (required)
   - `ADMIN_EMAIL` / `ADMIN_PASSWORD` — your admin login (required, min 10 chars)
   - `SESSION_SECRET` — auto-generated by Render
   - `MAIL_DOMAIN` — display domain for temp addresses (default `fasttempmail.site`; change when you own one)
   - `DEMO_MODE` — `true` while testing (shows the mail simulator + demo OTP codes); set `false` for production
   - `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` — optional, see step 5
   - `RESEND_API_KEY`, `RESEND_FROM` — optional, see step 7
4. Deploy. Watch the logs: you should see `[db] applied migration 0000_....sql`, `[db] admin account created for ...`, and `[db] default plan settings seeded`.
5. Open the free `https://<name>.onrender.com` URL and sign in with your admin email/password.

### 4. Verify the app

- Home page shows the **Generate Email** button; generating an address, copying it, refreshing the inbox, and the expiry countdown all work.
- Sign up with an email → in demo mode the 6-digit code is **shown on screen** (delivery isn't configured) → verify → wallet shows `$0.00` in the top bar.
- Deposit $3+ via Crypto → stays **pending** (honest gap, see below).
- Administration tab shows users, temp emails, transactions, plan settings, and Google sign-in.

### 5. (Optional) Google sign-in

1. In the app, go to **Administration → Google sign-in**. It shows the exact redirect URI for your deployment: `https://<name>.onrender.com/oauth/callback`.
2. In [Google Cloud Console](https://console.cloud.google.com) → your OAuth client → **Authorized redirect URIs** → add that exact URI.
3. Paste the Client ID + Client Secret into the app's form (or set the env vars before first deploy). The Google button goes live immediately.
4. For the future Pro "Gmail-connected mailbox", also set `GOOGLE_GMAIL_SCOPE=true` — it adds the Gmail read-only OAuth scope.

### 6. (Later) Connect your Hostinger domain

Your site works fine on the free `onrender.com` URL. When you're ready to use your own domain:

1. In Render → your service → **Settings → Custom Domains** → add your domain (e.g. `fasttempmail.example.com`). Render shows the DNS records it needs (a `CNAME` for subdomains, or `A` records for the root).
2. In Hostinger → **hPanel → Domains → DNS / Nameservers → Manage DNS records** → add exactly the records Render shows.
3. Wait for DNS propagation (minutes to a few hours). Render provisions a free HTTPS certificate automatically.
4. Update `GOOGLE_REDIRECT_URI` to `https://your-domain/oauth/callback` and re-add it in Google Cloud Console if you use Google sign-in.

### 7. (Optional) Resend email delivery

1. [resend.com](https://resend.com) free tier → verify your sending domain → create an API key.
2. Set `RESEND_API_KEY` and `RESEND_FROM` (e.g. `Fast Temp Mail <noreply@mail.example.com>`) in Render → redeploy.
3. After this, OTP codes are emailed instead of shown on screen (demo mode still shows the simulator button unless `DEMO_MODE=false`).

### Free-tier caveats (read before relying on it)

- **Idle sleep:** the free web service sleeps after 15 minutes without traffic. The first visit after sleep is slow (~30–60 s cold start), then it's fast again. A free cron ping every ~10 min keeps it warm if you want.
- **750 hrs/month** is enough for one service to run ~24/7 within the sleep/wake cycle.
- **512 MB RAM** is plenty for this app (Bun + small connection pool of 5).
- **Ephemeral disk:** files written to the container vanish on redeploy — fine, because all state lives in Supabase.
- **No credit card** is required for any of this.

## Environment variables

| Variable | Required | Description |
|---|---|---|
| `DATABASE_URL` | ✅ | PostgreSQL connection string (Supabase URI). Server fails fast with a clear error if missing. |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | ✅ | Admin account created on first boot only; never overwritten. Min 10 chars. |
| `SESSION_SECRET` | ✅ | Peppers stored session-token hashes. Changing it logs everyone out. Generate with `bun -e 'console.log(crypto.randomUUID()+crypto.randomUUID())'`. |
| `MAIL_DOMAIN` | – | Display domain for temp addresses (default `fasttempmail.site`). Change when you own a domain. |
| `DEMO_MODE` | – | `true` (default) shows the demo mail simulator and reveals OTP codes on screen when delivery isn't configured. Set `false` for production. |
| `DATABASE_SSL` | – | Set to `disable` only for local Postgres without TLS. Defaults to requiring TLS (Supabase needs it). |
| `PORT` | – | Server port (default `3000`; hosts set it automatically). |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_REDIRECT_URI` | – | Enables “Continue with Google”. Can also be set later in Administration → Google sign-in. |
| `GOOGLE_GMAIL_SCOPE` | – | Set to `true` to also request the Gmail read-only OAuth scope (future Pro feature). |
| `RESEND_API_KEY` / `RESEND_FROM` | – | Enables OTP + password-reset emails. In demo mode, codes are shown on screen instead. |

## Security notes

- There is no dev backdoor: no preview buttons, no seed actions, no way to obtain a session without credentials.
- Passwords: PBKDF2-SHA256, 210 000 iterations, unique salt. Admins can never see them.
- Sessions: 128-bit random tokens, stored as `SHA-256(SESSION_SECRET + ":" + token)`, 7-day expiry.
- OTP codes: 6 digits, 10-minute expiry, max 5 attempts, stored as hashes.
- Google OAuth: state + PKCE, `state` single-use with 10-minute expiry; client secret never leaves the server.
- Temp-mail inbox access: anonymous addresses are readable by anyone who knows the address id — that is how disposable mail works; owned addresses are restricted to their owner.
- All `/actions` requests are validated against zod schemas; unknown actions → 404, invalid payloads → 400.

## Honest limitations (not yet wired)

- **Simulated inbox:** generated addresses are display-only. Receiving *real* email needs a real domain plus an inbound email provider (e.g. a catch-all mailbox or an inbound-email API) wired to insert into `temp_messages`. The in-app "Simulate incoming mail" button is a clearly-labeled demo helper, not real delivery.
- **Resend:** without `RESEND_API_KEY`, OTP and password-reset emails cannot be delivered. In demo mode the codes are shown on screen instead; the app says so explicitly.
- **Crypto deposits:** deposits create a `pending` ledger entry (min $3). There is no payment-provider webhook yet — an admin verifies payments manually. Funds are never credited automatically.
- **Paid plans / Gmail-connected mailbox:** Gmail and Pro upgrades are requested in-app and activated manually by an admin for 30 days. Reading real Gmail needs Google OAuth credentials plus the Gmail API scope (`GOOGLE_GMAIL_SCOPE=true`) and is not implemented yet.
- **Monthly SMS numbers:** not built (Phase 2 — needs a Twilio-style number provider and real per-number cost).
